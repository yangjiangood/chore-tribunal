# 《家庭无情裁判所》开发过程说明文档

## 一、作品基本信息

- 作品名称：家庭无情裁判所
- 作品类型：AI 辅助开发的家庭家务积分与裁决系统
- 内网访问地址：`http://192.168.30.120:18080`
- 部署方式：Docker Compose 一键部署

## 二、项目背景与目标

《家庭无情裁判所》是一个面向家庭场景设计的家务积分与裁决系统，核心目标是把原本分散、模糊、容易引发争议的家庭家务记录，转化为结构化、可量化、可回溯、可展示的数据系统。

系统希望解决以下几个问题：

1. 家务分工难以长期记录，容易依赖记忆和主观印象。
2. 家务贡献缺少统一标准，容易产生“谁做得更多”的争议。
3. 缺少兼具趣味性和可视化效果的反馈机制，难以持续激励家庭成员参与。
4. 希望结合 AI 能力，根据真实数据生成“家庭裁决书”，提高系统的趣味性和表达效果。

基于以上目标，我设计并实现了一个包含“打卡、公屏排行、历史记录、成员管理、规则管理、数据分析、AI 裁决”的完整系统，并将其部署到可访问的服务器环境中，满足“可在公司内网访问”的参赛要求。

## 三、主要使用的 AI 工具/平台

本项目开发过程中，主要使用了以下 AI 工具辅助完成需求拆解、代码生成、界面优化、问题排查和部署：

1. Codex：用于前后端代码实现、问题修复、部署脚本补全、Docker 配置补全等。
2. ChatGPT：用于方案推敲、开发说明整理、文档撰写辅助。
3. 通义千问 / DeepSeek：用于思路补充、实现对比与提示词优化参考。

在整个开发过程中，AI 主要承担了代码生成、结构补全、修复建议、部署排障和文档草拟等核心工作；人工主要负责目标定义、结果判断、方向调整、界面偏好决策和少量参数修改。

## 四、系统功能说明

本系统当前已完成的主要功能如下：

1. 账号注册与登录。
2. 家庭成员管理，包括新增、编辑、停用、恢复启用、删除。
3. 家务规则管理，包括任务类型、分值、排序、启用/停用。
4. 打卡记分功能，可针对成员快速记录家务行为。
5. 公屏展示，包括排行、最近日志、规则入口等。
6. 历史记录页面，支持筛选、分页和下拉查询。
7. 分析页面，提供统计结果与趋势概览。
8. AI 裁决功能，基于家庭周数据生成“家庭裁决书”。
9. Docker 部署能力，包括一键部署脚本和更新脚本。

## 五、技术架构说明

本项目采用前后端分离架构，并结合容器化方式部署：

1. 前端：React + Vite。
2. 后端：NestJS。
3. 数据库：PostgreSQL。
4. 缓存：Redis。
5. 数据访问层：Prisma。
6. 部署方式：Docker Compose + Nginx 反向代理。

系统整体结构如下：

- 前端负责认证、打卡、公屏、控制台管理、历史记录和分析展示。
- 后端负责身份认证、成员管理、规则管理、事件记录、裁决生成、数据聚合等业务逻辑。
- PostgreSQL 负责持久化存储成员、规则、事件、偏好、裁决记录等业务数据。
- Redis 用于支撑缓存或实时相关能力。
- Nginx 用于托管前端静态资源，并将 `/api` 请求转发到后端服务。

## 六、AI 协作开发过程说明

### 1. 需求拆解阶段

在项目开始阶段，我先使用 AI 协助整理产品目标，将一个相对模糊的“家庭家务积分系统”需求，拆解为以下几个模块：

1. 认证模块：注册、登录、会话保持。
2. 公屏模块：成员展示、打卡入口、最近日志、排行展示。
3. 控制台模块：历史、规则、成员、分析、偏好设置。
4. 裁决模块：使用 AI 基于数据生成结构化裁决文案。
5. 部署模块：Docker 化、服务器部署、内网访问。

这一阶段 AI 的主要作用是帮助我快速完成“模块化拆解”和“前后端职责划分”，缩短从想法到系统原型的时间。

### 2. 前后端结构生成阶段

在确定模块后，我通过“明确功能目标 + 指定技术栈 + 指定文件范围”的方式，让 AI 分别生成：

1. 前端页面骨架与路由结构。
2. 后端模块划分与接口结构。
3. Prisma 数据模型与迁移方案。
4. 前端 API 调用层和状态管理逻辑。

例如，我会通过类似这样的提示思路推动开发：

- “基于 React + Vite 实现一个家庭家务积分公屏页面，保留成员选择、打卡规则、排行、日志区域。”
- “基于 NestJS + Prisma 实现成员管理接口，支持新增、停用、恢复启用和删除。”
- “为当前项目补齐 Dockerfile、docker-compose 以及 Nginx 反向代理配置。”

AI 在这一阶段承担了大量基础代码生成工作，我再根据实际运行结果逐步调整。

### 3. 界面优化阶段

系统初版完成后，我将重点放在用户体验优化上，并持续借助 AI 对界面进行迭代。主要优化内容包括：

1. 认证界面布局协调性优化。
2. 注册切换时滚动条问题修复。
3. 打卡界面弹层标签布局优化。
4. 弹层数据过多时增加滚动区域。
5. 成员管理界面补充“恢复启用”能力。
6. 修复恢复启用后界面状态不刷新的问题。
7. 去掉分析页、历史页、规则页、成员页、偏好页中的重复标题和说明性文字。
8. 优化历史页筛选区和分页按钮间距。

在这个过程中，AI 的价值主要体现在：

1. 快速定位前端组件文件。
2. 根据具体 UI 问题输出可执行修改方案。
3. 反复微调样式和交互，直到界面更贴近预期。

### 4. 业务逻辑修复阶段

随着功能逐步完善，我开始用 AI 协助排查实际使用中的问题，包括：

1. 成员恢复启用后前端状态不刷新。
2. 云端部署后浏览器环境下 `crypto.randomUUID()` 不可用。
3. AI 裁决接口在不同环境下的降级问题。
4. Docker 构建阶段 Prisma 所需环境变量缺失问题。
5. 后端生产环境启动入口路径错误问题。
6. 容器内依赖下载超时、npm 源过慢等问题。

这部分工作体现了 AI 在“排障”和“修复闭环”上的作用：我负责提供错误现象、日志输出和目标效果，AI 则快速给出原因判断、修改方案和补丁建议，再由我进行验证。

### 5. 部署与上线阶段

部署阶段同样高度依赖 AI 协作完成，主要工作包括：

1. 补齐前后端 Dockerfile。
2. 增加生产环境 Docker Compose 文件。
3. 增加 Nginx 配置，实现前端静态托管与 `/api` 反代。
4. 增加 `.env.prod.example` 环境变量模板。
5. 增加 `deploy.sh` 和 `update.sh`，实现一键部署与一键更新。
6. 根据服务器问题持续修正构建、启动、依赖下载和浏览器兼容问题。

最终，系统成功部署并可在内网通过地址访问，满足比赛“公司内网可体验”的要求。

## 七、提示词（Prompt）设计思路

本项目在与 AI 协作时，并不是简单地“一次性让 AI 生成整个系统”，而是采用分阶段、分模块、逐步收敛的提示策略。主要思路包括：

1. 明确目标：每次只要求 AI 解决一个清晰问题，例如“修复注册切换时滚动条问题”。
2. 指定范围：尽量明确文件路径、模块名称、页面位置，减少无关改动。
3. 强调限制：例如“不改变主交互结构”“去掉重复标题”“只优化布局不改业务逻辑”。
4. 结合反馈迭代：我会在运行后把真实问题再反馈给 AI，例如“恢复启用后 UI 状态没有刷新”，再让 AI 做二次修正。
5. 面向落地：在部署阶段，我更关注“是否能在服务器跑起来”，因此会直接要求 AI 补齐 Docker、Compose 和一键脚本，而不是停留在理论方案层面。

这种提示方式让 AI 更像一个协作开发助手，而不是单次问答工具，从而显著提高了开发效率。

## 八、系统如何使用

系统当前使用方式如下：

1. 通过浏览器访问内网地址进入系统。
2. 使用账号登录系统。
3. 在公屏界面选择家庭成员和任务规则，进行打卡记分。
4. 在控制台页面查看历史、成员、规则、分析等内容。
5. 在裁决功能中生成基于周数据的 AI 裁决结果。
6. 管理员可在成员和规则页面维护系统基础数据。
