# 家庭无情裁判所 技术选型与架构方案

## 1. 文档目标

本文档用于冻结「家庭无情裁判所」第一阶段的技术选型与系统架构边界，作为前端开发、后端开发、数据库设计和部署规划的统一依据。

本文档基于以下既定结论：

- UI/UX 主方向选择 `方案 A：公屏审判报`
- 局部视觉融合 `方案 B：综艺战情室`
- 首页大屏视觉采用 `自定义高保真实现`
- `shadcn/ui` 不主导首页大屏视觉，只用于控制台和通用交互组件

## 2. 需求特征分析

### 2.1 产品类型

本项目本质上不是内容站，也不是 SEO 驱动产品，而是：

- `平板横屏 Web 应用`
- `强交互公共屏`
- `家庭内部使用工具`
- `本地模式 + 云端模式并存`

### 2.2 核心技术约束

| 维度 | 判断 |
| --- | --- |
| SEO | 基本不敏感 |
| 交互复杂度 | 高 |
| 实时性 | 中等偏高 |
| 设备目标 | iPad / 平板横屏优先 |
| 离线能力 | 必须支持 |
| 本地持久化 | 必须支持 |
| 多端查看 | 云端模式需要 |
| AI 集成 | 后端统一接入 |

### 2.3 技术重点

本项目真正要解决的技术问题不是 SSR，而是：

1. 首页大屏常驻时的流畅性
2. 两步打卡的低延迟反馈
3. 单机模式的数据可靠保存
4. 云端模式下的最终一致性
5. 打卡撤销窗口与事件状态管理
6. AI 判决流程的稳定触发与降级

## 3. 最终技术选型

## 3.1 选型结论

| 层级 | 选型 |
| --- | --- |
| 前端框架 | `React + Vite + TypeScript` |
| 样式系统 | `Tailwind CSS` |
| 通用组件 | `shadcn/ui` |
| 首页大屏实现 | 自定义组件 + Tailwind + 设计令牌 |
| 后端框架 | `NestJS` |
| 数据库 | `PostgreSQL` |
| ORM | `Prisma` |
| 缓存/会话/辅助 | `Redis` |
| 本地存储 | `Dexie.js`（封装 IndexedDB） |
| 音效 | `Howler.js` |
| 设备反馈 | Web API（按浏览器能力降级） |
| 实时通信 | `SSE` |
| 部署形态 | `Docker Compose` 优先 |

## 3.2 选型理由

### React + Vite + TypeScript

适合原因：

- 当前仓库前端已是 `React + Vite`
- 更适合纯交互型应用
- 无 SEO 压力，不必为 SSR 付出复杂度
- 本地开发启动快，适合高频迭代

### Tailwind CSS

适合原因：

- 适合高保真定制大屏布局
- 适合做横屏板式、复杂层级和状态样式
- 能快速沉淀设计令牌

### shadcn/ui

定位说明：

- `用于控制台、表单、弹窗、抽屉、Toast、Tabs、Select、Dialog`
- `不用于首页主视觉结构`

原因：

- 首页主屏需要高辨识度与强视觉风格
- shadcn/ui 更适合稳定、规范的后台与操作型界面
- 如果用它主导首页，容易把产品做成普通管理后台

### NestJS

适合原因：

- 当前仓库后端已是 `NestJS`
- 模块化明确，适合后续扩展
- 适合承接账号、家庭、规则、事件、AI、SSE 等服务拆分
- 对 TypeScript 一体化协作友好

### PostgreSQL + Prisma

适合原因：

- 数据结构高度关系型
- 成员、家庭、规则、事件、周报、档案天然适合关系模型
- Prisma 适合快速建模和类型共享

### Redis

适合原因：

- 支持会话、临时状态、撤销窗口、排行榜缓存
- 后续也可承接限流、事件广播辅助、SSE 辅助状态

### Dexie.js

适合原因：

- 比 LocalStorage 更适合结构化事件存储
- 适合离线队列、日志、本地档案、最近标签缓存
- 对 IndexedDB 做了较好封装

### Howler.js + Web API

适合原因：

- Howler.js 适合统一管理点击音效和判决音效
- Web API 可承接浏览器允许范围内的触觉和全屏能力

注意：

- 震动能力不能当核心功能承诺
- 尤其 iPad 场景下必须视为可选增强

## 4. 为什么不选其他方案

## 4.1 为什么不选 Next.js 作为主框架

不选原因：

- 本产品不依赖 SEO
- 核心价值在强交互和本地模式
- 已有前后端骨架是分离式
- 引入 Next.js 会重构边界，收益有限

## 4.2 为什么不以 Supabase 为主后端

不选原因：

- 事件撤销与待确认状态较复杂
- AI 判决和周归档有明确业务流程
- 家务事件与排行榜有较强领域逻辑
- 长期来看自控后端更稳

Supabase 适合做 MVP 快速验证，但不适合作为当前明确架构主线。

## 5. 系统架构总览

## 5.1 分层结构

```text
前端展示层
  ├─ 首页大屏（自定义高保真）
  ├─ 控制台（shadcn/ui + 自定义）
  ├─ 本地数据访问层（Dexie）
  └─ API / SSE 客户端层

后端应用层
  ├─ Auth 模块
  ├─ Family 模块
  ├─ Member 模块
  ├─ TaskRule 模块
  ├─ Event 模块
  ├─ Verdict 模块
  ├─ Archive 模块
  └─ Realtime 模块（SSE）

基础设施层
  ├─ PostgreSQL
  ├─ Redis
  ├─ OpenAI API
  └─ 对象/文件存储（后续可选）
```

## 5.2 前后端职责边界

### 前端负责

- 首页大屏渲染与即时交互反馈
- 本地模式数据读写
- 云端模式本地缓存与离线事件暂存
- 打卡两步交互
- 控制台表单与设置面板
- 音效、全屏、局部动效

### 后端负责

- 家庭账号与登录态
- 家庭成员与规则配置
- 云端事件写入与撤销
- 周档案、数据分析、AI 判决聚合
- SSE 状态广播
- 统一的 AI 调用与降级控制

## 6. 前端架构建议

## 6.1 模块划分

建议将前端拆为以下模块：

- `app-shell`
- `board-screen`
- `task-panel`
- `ranking-board`
- `public-log`
- `verdict-modal`
- `control-center`
- `local-store`
- `api-client`
- `realtime-client`
- `audio-engine`

## 6.2 视觉实现原则

### 首页主屏

- 完全自定义
- 以 Tailwind + 设计令牌为核心
- 不使用 shadcn/ui 的卡片拼装思路主导布局

### 控制台

- 优先使用 shadcn/ui
- 再通过主题变量和样式扩展统一视觉

## 6.3 状态管理建议

第一阶段可不引入重型全局状态库，先采用：

- React 本地状态
- Context 仅承载少量全局状态
- 数据读取与同步由自建 service 层控制

如果后续复杂度明显上升，再考虑引入：

- TanStack Query
- Zustand

当前阶段不建议过早增加抽象层。

## 7. 后端架构建议

## 7.1 NestJS 模块拆分

建议最少拆为：

- `auth`
- `families`
- `members`
- `task-rules`
- `events`
- `archives`
- `analytics`
- `verdicts`
- `realtime`
- `preferences`

## 7.2 关键服务职责

### AuthService

- 极简账号注册
- 登录
- 登录态刷新
- 已登录状态下修改密码

### EventService

- 创建打卡事件
- 标记待确认 / 正式状态
- 撤销事件
- 计算当前排行快照

### VerdictService

- 汇总本周数据
- 组装 prompt
- 调用 OpenAI
- 失败时降级为本地模板

### RealtimeService

- 维护 SSE 订阅
- 在事件创建、撤销、归档后推送最新状态

## 8. 部署建议

## 8.1 开发阶段

采用 `Docker Compose`：

- `frontend`
- `backend`
- `postgres`
- `redis`

## 8.2 第一阶段上线建议

优先维持简单：

- 前端静态部署
- 后端容器部署
- PostgreSQL 单实例
- Redis 单实例

不建议一开始就上 K8s 或微服务拆分。

## 9. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 首页视觉过于依赖组件库 | 主屏失去辨识度 | 首页坚持自定义实现 |
| 本地与云端数据边界不清 | 同步与撤销混乱 | 明确真相源与同步规则 |
| 过早引入复杂状态管理 | 开发速度下降 | 第一阶段保持轻量 |
| 震动 API 兼容性不足 | 体验不一致 | 将其视为增强能力而非核心承诺 |
| SSE 与事件状态设计不清 | 多端数据错乱 | 使用事件状态机与快照推送 |

## 10. 最终结论

当前项目正式采用以下技术主线：

- `React + Vite + TypeScript`
- `Tailwind CSS + shadcn/ui`
- `NestJS`
- `PostgreSQL + Prisma`
- `Redis`
- `Dexie.js`
- `Howler.js + Web API`
- `SSE`

其中最关键的架构约束是：

1. 首页大屏视觉必须自定义，不由 `shadcn/ui` 主导
2. 控制台优先使用 `shadcn/ui`
3. 单机模式以本地存储为主
4. 云端模式以 PostgreSQL 为真相源

后续开发默认以本方案为基础推进。
